## 1. Resolved — the outage was radio sleep, not a reboot

**Measured root cause.** After the head was woken from the Android app, all four ports returned
(22/8090/8080/9090) and `uptime` settled the question:

```
uptime_min=334.2   at Sat Nov 14 02:13:14 UTC 2026   -> booted ~20:39 Nov 13
/tmp/polaris-astro-boot.log: "Fri Nov 13 20:39:05 UTC 2026 polaris-astro boot hook"
```

The boot log timestamp matches `/proc/uptime` exactly, and the hook marker is present in
`/app/network_telnetd.sh` (`grep -c "polaris-astro boot hook"` → 1). The device had been up
continuously since 20:39 — **it never rebooted during this session**, and the boot hook ran
fine. This was plain radio sleep: the firmware powers the Wi-Fi down 60 s after the last client
disconnects, and while the mount is unaligned `wifi-keepalive` deliberately will not hold a
connection open (connecting unaligned triggers the Benro compass-calibration prompt).

**Two earlier claims are withdrawn:**
1. *"Rebooted to stock"* — inferred from a `GoAhead-Webs` banner that was **never the Polaris**.
2. *"ENOSPC killed the boot hook"* — plausible-looking (`install_astro.sh:127-129` documents
   exactly that failure) but contradicted by uptime and the hook marker.

### 1.1 The `192.168.0.1` collision — why the outage was misdiagnosed
While the AP was down, `192.168.0.1` still answered on :80/443. It was **not** the Polaris:
the browser rendered **"CGNV4-FX4 Login — Hitron Technologies"**, a router admin page. My host
sits on `192.168.68.0/24` (gateway `.68.1`), so when the AP disappeared, traffic to
`192.168.0.1` was routed to the ISP modem instead.

**Consequence for future diagnosis:** a live :80 on `192.168.0.1` is not evidence the head is
up. Confirm with `/api/link` returning our JSON, or check the page title, before concluding
anything about patch state. A bare TCP connect or HTTP 200 can be answered by a different device.

### 8.1 Ownership and repository boundaries

Primary implementation repositories:

1. ian-morgan99/libgphoto2 — normative Pentax/IMAGE Transmitter 2 protocol,
   direct-camera tests, and the reusable camera contract.
2. ian-morgan99/BenroPolarisPatcher — consumer shim/firmware package and A/B
   runtime qualification.

Supporting repositories are evidence and integration surfaces only:
PrivateResearch (static/decompiled evidence and provenance), BenroHardwareValidator
(replay/package/runtime/hardware gates), and OpenPolaris (client/UI/C-path
integration). Do not modify the current dirty OpenPolaris checkout owned by its
active agent.

Use one canonical checkout/worktree per primary repository. Do not create
additional worktrees, reset or rebase another agent's active branch, or mix
Astro solver changes into a camera commit. One active writer per checkout; the
WBS and issue comments are the handoff surface.

### 8.2 Branch, merge, release, and review policy

- main is the integration/release branch. A camera change enters main only as
  a small reviewable commit with exact tests and dependency SHA in this WBS.
- Use a short-lived camera branch only when the canonical checkout is free.
  Merge it; do not copy changes or cherry-pick ad hoc. Delete it only after
  the merged commit and evidence are confirmed.
- The Patcher Astro feature branch is not a camera integration branch. A
  camera-only documentation commit there preserves handoff only; it is not a
  release and must not be pushed to main by the camera agent.
- Before every merge/release record status, exact HEAD/upstream SHAs, diff
  check, clean build, tests, package hashes, loader proof, and A/B/C gate.
- Scheduled ChatGPT review is a review gate, not a test substitute. For every
  stable camera slice review the diff, IT2 anchors, failure classification,
  output, provenance, and rollback path; report PASS, CONDITIONAL, or BLOCKED.
- Never replace a qualified artifact with an unqualified rebuild. Publish an
  immutable artifact with a manifest and retain the prior release.

### 8.3 Evidence and ownership rules

Use the #149 grades: A = physical camera evidence with exact provenance and
readback/restoration; B = deterministic host/Patcher runtime with exact loaded
library and trace; C = diagnostic/replay narrowing only; D = unproven or
consumer-only; E = disproven.

A Benro Connect/OpenPolaris failure is discovery evidence until it reproduces
at the libgphoto2 boundary. PTP 0x2001 acknowledgement, non-error return,
timer/echo, preview frame, or output file alone does not prove application.

### 8.4 Completion gates

C0 provenance: record exact libgphoto2 and Patcher commits, firmware/package
hashes, loaded ptp2.so/camlib paths and hashes, camera model/firmware, and mode.

C1 IT2 contract: trace every advertised control through the decompiled model/UI
gate, value list, serialization, transport, response, condition polling, and
teardown. Reconcile IMAGE_TRANSMITTER_CAPABILITY_MATRIX.md,
IMAGE_TRANSMITTER_SETTING_PATH.md, and REAL_HARDWARE_TEST_LOG.md. Names,
adjacent opcodes, DeviceInfo, or a GetSet descriptor are not support proof.

C2 direct baseline: build a clean exact libgphoto2 SHA, attach the camera
directly, prove the running harness loads that exact library/camlib, and capture
the first failing PTP operation/state. Writes require advertised value,
changed readback, exact restoration, and fresh-session verification.

C3 matrix: for each supported model qualify startup/discovery, conditions,
ISO/shutter/aperture/EV read/write/restore, source-supported focus/AF,
preview ON/GET/OFF, ordinary capture, RAW/JPEG/RAW+JPEG, repeated capture,
timed and untimed Bulb, cancellation, processing, reconnect, power cycle, and
post-workflow capture. One variable per gate; stop at the first mismatch.

C4 Bulb state machine: requested -> accepted -> exposure -> processing ->
candidate/file events -> transfer -> complete, with separate cancelled,
timed_out, and recovery paths. Manual and Astro timing are separate. Timer or
echo is not completion; record every event and output obligation.

C5 Patcher A/B: rerun the same matrix through the local packaged runtime and
prove package hashes, loader paths, shim selection, and firmware provenance.

    A direct fail + B fail at the same lower-level operation => candidate libgphoto2 defect
    A direct pass + B fail => Patcher/package/shim/runtime defect
    A direct pass + B pass + C fail => OpenPolaris/client defect

Do not change libgphoto2 for a B-only or C-only failure.

C6 physical release: direct evidence, restoration, repeated capture,
Bulb/cancel/recovery, install/rollback hashes, and negative containment are
required. Green build or installed-successfully is not qualification.

- **2026-11-14 — extraction optimised: 1792 ms -> 1215 ms on device (32%), output byte-identical.**
  Followed the #342 ranking, which put `polaris-extract` at 47% of capture-to-result.

  **Where the time actually goes.** A phase probe (temporary, not committed) split extraction on the
  head: decode ~240 ms, per-tile background/noise ~120 ms, flood fill ~1430 ms. The flood fill looked
  like the target, but counters showed it only touches ~50k pixels; the cost is the *outer scan*, which
  evaluates `map_at()` twice per pixel — **4.9M calls for 2.46M pixels**, each doing two floating-point
  divisions. ARMv7 division is slow, and `fx` depends only on x while `fy` depends only on y, so both
  were being recomputed 4.9M times for values that repeat every `tile` pixels.

  **The fix.** `build_weight_tables()` hoists per-x and per-y weights into six arrays of W or H doubles
  (~25 KB on 1920x1280); the inner loop becomes four multiplies with no division. Products are formed in
  exactly the order `map_at()` forms them, so results are bit-identical. Falls back to `map_at()` if any
  allocation fails.

  **Two attempts that failed, recorded because they were nearly shipped.**
  1. A precomputed per-pixel threshold map (19.7 MB) was *slower* — 1843 ms vs 1760 ms. It did the same
     4.9M interpolations and then added a second pass over every pixel plus 19.7 MB of traffic.
  2. Replacing the two divisions with one reciprocal was byte-identical at the default `tile=64` but
     **changed star positions at `tile=48`**. `tile=64` is a power of two, so the reciprocal is exact
     there and hides the error; non-power-of-two tiles expose it. Kept the division.

  **Why the first test was replaced.** The initial guard compared star lists between hoisted and
  un-hoisted builds. It passed against a deliberately wrong interpolation weight — that mutation changed
  the threshold at **1,178,134 of 2,457,600 pixels** and still emitted byte-identical stars, because the
  blobs are bright enough that a shifted background does not change which pixels clear the threshold. A
  differential that cannot see a real numerical error reads as coverage while proving nothing. Added
  `--dump-thresholds`, which prints each pixel's threshold computed *both* ways at full precision; the
  test asserts bit-for-bit equality for every pixel across tile sizes 64/48/37. That guard fails on all
  three tiles under the mutation, and passes clean on the real frame (0 mismatches of 2,457,600).

  **Verification.** Byte-identical star lists on ARM at ds=1/2/4 and for the `--focus-metric` path
  (`score=128973.6087 hfr=1.0104 stars=300 sharp=4.3437`). Valgrind: 0 bytes in use at exit, 0 errors —
  same as the original. Full suite 813 passed (+8 new). Device, 7 runs: ds=1 1792->1215 ms, ds=2
  595->447 ms.

  **Effect on the #342 ranking** (re-measured, `docs/evidence/bench-342-20261114/device-after-*.jsonl`;
  meta records prove `polaris_extract_md5` went 1224d8b1 -> 0007e8c0): warm total **3800 -> 3250 ms**,
  cold **4230 -> 3640 ms**. Extraction falls from ~47% to ~38%, and quad search becomes #1 at ~50%.
  Quad search and index load are flat within noise, which is the control that says the improvement is
  real rather than global drift. 10/10 runs still solve on index-4117 with logodds 87.8.

  I first wrote "total moves to ~3.14 s warm", which was arithmetic on the extraction delta rather
  than a measurement; the measured figure is 3.25 s. `total_ms` includes process start-up and the star
  file round-trip, which the per-stage timings do not.
- **2026-11-14 — #344 parameter sweep: star count is the knob, `--depth` is not.**
  New `tools/bench-solve-params.sh`, run blind on the head against all ten indexes. Evidence in
  `docs/evidence/sweep-344-20261114/`.

  **Solve time is minimised near 200 stars, not at the low end.** 50 stars -> 23.8 s, 100 -> 3.4 s,
  200 -> 1.57 s, 300 -> 1.81 s, 400 -> 3.46 s. A starved field is fifteen times slower than a well
  fed one: with too few detections the solver exhausts its candidate quads and falls through to a much
  wider search. This independently supports #341's `max_stars=200` -- it sits near the bottom of the
  curve, not merely "high enough". Confidence rises monotonically (logodds 55.9 at 100 -> 137.2 at 400),
  so 200 is a real speed/quality trade-off rather than a free win.

  **`--depth` does not behave as documented and should not be used to bound cost.** The help says
  "stop after the brightest N stars". Measured: depth 1-2 return in under 2 ms (search exits
  immediately), so the flag does reach `solver->endobj`. But its effect depends on the field in a way
  nothing documented predicts -- at 200 stars depth 3 solves with timing identical to uncapped, while
  at 50 and at 400 stars the same value fails outright. Where it does bite it can make things worse:
  at 50 stars, depth 3->6 raised a failing run from 0.33 s to 8.9 s, and depth 8-10 blew past a 12 s
  cpulimit. `nfield` always reports the full detected count (`starxy_n(field)`), so it cannot be used
  to confirm the cap was applied -- which is why this is easy to mistake for working.

  I wrote an earlier draft claiming "at 3 and above it does nothing measurable". That was wrong: it
  came from one 400-star probe where depths 50/100/400 happened to time identically. Re-running across
  star counts showed depth 3 failing at both 50 and 400 stars. Corrected in the evidence README before
  commit; the lesson is that a single-pointing probe is not evidence about a flag's semantics.

  **Consequence:** `--max-stars` controls solve time, `--cpulimit` is the only reliable hard bound, and
  `--depth` should stay unset (0). The help text promising behaviour the binary does not deliver
  consistently is worth raising separately rather than picking a depth value that happens to work for
  one pointing.
