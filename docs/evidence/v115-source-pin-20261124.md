# v115 source pin: is the inspected ARM binary really 6.0.0.54.115?

Resolved 2026-11-24 after a harness conversation stopped mid-answer with the
open worry *"the ARM binary I inspected lacks v115's markers, so it may not be
the v115 packet at all."* That worry was half right and half a false alarm. This
record settles both halves so the derivation is not repeated.

## Question

Was the Stage-2 binary used by the ARM emulation gate actually built from the
v115 candidate, or from some other tree? And if it is v115, is reading source at
`main` a valid way to reason about its behaviour?

## Answer 1 — the binary IS v115. The missing marker was the wrong probe.

`strings` on the ELF returns **zero** hits for `6.0.0.54.*`. That is expected, not
suspicious: the display version is a packet-level stamp and never appears inside
the Stage-2 shared object. Proving provenance requires the packet artifacts, not
the binary's own strings.

| Artifact | Value |
|---|---|
| `FwPkt/FwVer` | `FwVer:6.0.0.54.115;date:2026.11.22;` |
| `RELEASE-IDENTITY.md` | display fw `6.0.0.54.115`, build id `astro-v115-k01-camera-admission-20261122` |
| Binary SHA-256 | `fcce947ff5525629f23552fd7ff3feb3e377512dd957522fc95191689bcc1bfb` |
| Manifest expectation | `manifest_expected_sha256` — **identical**, size 7,801,576 both sides |

Binary path (still present):
`/home/ian/polaris-v101/out/astro-v115-k01-camera-admission-20261122/stage2-ondisk/ondisk/pgphoto.stage2ondisk`

The ledger binds the version to its commits, line 156 of
`docs/RELEASE-VERSION-STATE.md`:

```
version_commit_binding=6.0.0.54.115|libgphoto2=0f2f34e0004011136fa75bf43e215acc0c8b9fdb|patcher=f67c6baf5f572073c3fb0890f4e68b1d631de0fa
```

### The `patcher_commit` discrepancy is benign

`arm-emulation-record.json` records `patcher_commit = 34e28bb`, while the identity
file and ledger say `f67c6ba`. Both are correct and they differ for an
accounted-for reason: `34e28bb` is the *claim* commit ("chore(release): claim
6.0.0.54.115"), written after the build so "both clones agree" rather than leaving
the builder tree dirty. Its own message explains this.

Verified non-issue: `f67c6ba..34e28bb` touches only
`docs/RELEASE-VERSION-STATE.md` and `tests/run_prerelease_gate.sh` — **no built
code**. The emulated bytes are the v115 build either way.

## Answer 2 — source at `main` is NOT a valid proxy for v115 behaviour

The binary was built from `f67c6ba`. `main` is **27 commits ahead**, and 8 of those
touch shipped or release-path code:

```
container/stage2_loader.c                        | +32   <- the Stage-2 loader itself
scripts/release/release-fwpkt.sh                 | +65
scripts/release/install-astro-kit.sh             | +13
container/governor-replay/replay.c               | +18
tests/run_prerelease_gate.sh                     | +27
container/test_stage2_capture_composition.{c,sh} | +25
tests/test_canary_two_shot.py                    | +21
```

So a claim of the form "the code does X", read off the working tree, can describe
behaviour that is **not in the shipped packet**. Read pinned instead:

```bash
git show f67c6baf5f572073c3fb0890f4e68b1d631de0fa:container/stage2_loader.c
```

### Severity of the drift, per file (verified, not assumed)

- **`container/stage2_loader.c` — trace-only, non-behavioural when tracing is off.**
  The additions are `capture-enter`/`capture-return` field enrichment and a new
  `stage2_trace_wait_event` wrapper. The wrapper is only installed behind
  `stage2_capture_trace_enabled()` (`stage2_loader.c:2103`), and the trace prints
  are behind the same predicate. With tracing disabled the resolved core target is
  returned unchanged, so v115's runtime behaviour matches `main` for this file.
- **`scripts/release/install-astro-kit.sh` — behavioural, but host-side.**
  The single SSH reachability probe became a 6-attempt retry with 10 s backoff
  (measured 2026-11-23: probes returned in 3.2 s, timed out at 5 s twice, hung past
  30 s once). Still fail-closed after 6 attempts. This is the host installer, not
  the on-device payload, so it does not change what v115 runs on the camera — but
  it does mean install logs from a v115-era run look different from today's.

## Is there a v116? No.

`grep` for `6.0.0.54.116` / `astro-v116` across both clones returns nothing.
Current state in both clones is identical:

```
last_display_fwver=6.0.0.54.115
consumed_display_fwver=6.0.0.54.115   (and .108 earlier)
```

Nothing claims or reserves `.116`; the next build would take it.

## Reusable rule

Provenance of a built candidate is established by **`FwVer` + `RELEASE-IDENTITY.md`
+ manifest SHA**, never by grepping the ELF for a version literal. To reason about
a shipped version's behaviour, resolve its commit from `version_commit_binding` and
read that blob — then classify drift as behavioural or trace-only before concluding
anything about runtime differences.

Related: `docs/FWPKT-PROVENANCE-CONTRACT.md`, `docs/RELEASE-IDENTITY-PROCESS.md`,
and gate arm **R5** in `scripts/release/check-release-gates.py` (build-time shipped
payload currency, `SHIPPED_PATHS = ("container/astro/ondisk", "build-astro.sh")`).
R5 guards the *forward* direction — that a build's payload matches the commit it
claims. This record covers the reverse direction: reading source for a packet that
was already built and shipped.
