## The `ov` finding and the correction to the previous recommendation

The prior response called the blank `ov:` value a concrete defect. That was too strong. A repository-wide check found **138 recorded code-780 replies with an `ov` field**, covering stock `sw:8.0.0.76` (including records without `exAxis`) and patched `sw:6.0.0.54.52`, `.60` and `.61`; all have `ov: ;`. The `.62` reply was captured in this session and also has the correct `sw:6.0.0.54.62` with blank `ov`.

Static inspection of the candidate `polestar_app` now explains the empty field. `SP_GetDeviceVer` at `0x13f804` builds the firmware strings; `SP_PushDeviceVer` at `0x13fc58` formats code 780. The latter checks `SP_OmsCtx()+0x6d`. When false it uses the literal format `hw:%s;sw:%s;exAxis:%s;sv:%d;ov: ;`; when true it formats `ov:%s` from `SP_OmsCtx()+0x6e`. `OmsTask` initializes the flag false and sets it true in the state branch that requests an OMS version with `SP_BtMsgGetOmsVer(1)`. I extracted the `.62` candidate appfs (`polestar_app` SHA-256 `700f1ef6…`) and confirmed its `SP_PushDeviceVer` disassembly matches the earlier app binary at this function. The evidence therefore supports `ov` as a conditional OMS-version field deliberately blank when the OMS-version state flag is inactive, not as the Polaris firmware display field. This resolves the code-side question; it does not prove how every Benro Connect version handles the field, but there is no evidence that blank `ov` caused the camera-on crash.

Device verification for this check: associated BSSID `48:E7:DA:D4:B5:73` / SSID `polaris_d13e86`, route via `wlp8s0`, and SSH reports `/app/FwVer:6.0.0.54.62`. The request used the one-shot `app-burst.py --group identity` handshake; it sent no shutter command. Camera USB was absent and Mlog contained no corresponding native-app `code:780` transaction. Thus we have a valid `.62` response, but not a native Benro Connect error trace. A check of `adb devices` showed none, but ADB is not part of this project's current workflow and its absence is not a blocker.

The crash-moment replay had two tooling traps: the earlier `app-burst.py` sent type-2 requests for camera-state codes that the real app sends as type 1, and its frame parser discarded additional replies coalesced in one TCP read. The updated replay fixes the request framing, registers/drains a client session, and retains extra/partial frames across queries and timeouts. Focused regression tests cover both cases; the replay is now suitable as a diagnostic tool, but its replies remain a separate client session and cannot substitute for the native app's captured traffic.
