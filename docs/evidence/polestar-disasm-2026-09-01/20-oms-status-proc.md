# 20 — OmsUpgradeStatusProc state machine (0x75bfc, 2904 bytes)

> Evidence collected 2026-09-01. Status: **partial** — only call-graph and
> structural overview; individual state bodies not yet disassembled.
> The function is the **post-FwPkt-update state engine** that runs on the
> OmsUpgrade thread. It is woken by `OmsUpgradeMsgProc` (0x768e8) for each
> OMS message and drives the gimbal upgrade state transitions.

## Inferred state machine (5 named commands + 2 ack paths)

```
[wait msg] -> r12 (case 0)
   |
   v
OmsUpgradeCmdStart (0x75804)  <- r12=1, jump to 0x75d50
   |--> sets initial state
   |--> arms OmsUpgradeTimeOut
   v
OmsUpgradeCmdData (0x75a54)  <- r12=2, jump to 0x75db8
   |--> repeated: receive data chunks
   |--> arms OmsUpgradeTimeOut after each
   v
OmsUpgradeCmdDataEnd (0x758fc)  <- r12=2 path end, jump to 0x75ec0
   |--> final data chunk
   |--> arms OmsUpgradeTimeOut
   v
SP_OmsUpgradeCheckFwPkt (0x76f24)   <-- file 18 (FWPkt check)
   |--> verifies FwPkt integrity
   v
SP_OmsUpgradePushResult (0x779a0)
   |--> reports result back to BT host
   v
SP_OmsUpgradePushStateAck (0x77c90)  <- r12=ack path
   |--> final state transition
   v
[wait msg] -> r12 (case 0)
   ^
OmsUpgradeCmdCancle (0x758bc)  <- r12=7 path, jump to 0x7630c
   |--> abort path
```

The 5 `OmsUpgradeTimeOut` calls in the scan suggest the state machine is
**timer-driven** — each state arms a watchdog, and an unhandled timeout
restarts the state (recovery logic).

## Unresolved

- The 0x2904 byte body of OmsUpgradeStatusProc has not been fully disassembled
  (TODO for next investigator). The 5 TimeOut call sites suggest 5 distinct
  state arms, but their switch/case structure is not yet fully mapped.
- The data flow between OmsUpgradeCmdData (0x75a54) and the s_stOmsCtx
  structure (0x278-byte context, see file 16) is not yet traced.
- Cases 3, 4, 5, 6, 8, 9, 10 of the jump table are not named — what state
  do they represent? (likely "data received", "verify", "install", "complete",
  "fail", "rollback", "retry")
- The OmsUpgradeCmdStart entry at 0x75d50 is the **first** action — but
  what initial state does it set? Need to disassemble 0x75d50..0x75e7c.
- OmsUpgradeCmdCancle is reached from 0x7630c — the cancel path is in
  the "after SP_OmsUpgradeCheckFwPkt" region. What triggers it? A failed
  FwPkt check, or an explicit user cancel via BT message?
