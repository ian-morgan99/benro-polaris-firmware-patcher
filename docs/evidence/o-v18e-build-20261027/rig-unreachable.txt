CORRECTION: an earlier version of this file recorded "port 80 OPEN" and inferred
"the rig is up but sshd is not listening". That was WRONG. The host answering
192.168.0.1 on port 80 is the HOME ROUTER, not the gimbal.

Proof:

    $ curl -A 'VSCode-LMStudio-Bridge' http://192.168.0.1/login.html
    <title>Log in to Common Router - Hitron Technologies

The router serves GoAhead-Webs on port 80 -- the same banner the gimbal uses --
so a banner check cannot tell them apart. The discriminator is the route:

    $ python3 scripts/wait-for-rig.py
    NOT_READY WRONG_NETWORK -- 192.168.0.1 is answered via enp11s0, not wlp8s0;
    that is the home router sharing the address, not the gimbal. Associate to the
    gimbal AP (polaris_*) on wlp8s0.

    /sys/class/net/wlp8s0/carrier  -> 0     (not associated)
    /sys/class/net/wlp8s0/operstate -> down
    /sys/class/net/enp11s0/carrier  -> 1     (Ethernet, carries the default route)

So: the host is on Ethernet via the Hitron router, and wlp8s0 is down. The gimbal
has not been reachable at all during this window -- every "port 22 refused" and
"port 80 open" observation was the router. This is the exact failure mode
docs/FIRMWARE-INSTALL-PROCESS.md and the fwpkt-update-flow skill warn about
("reject the Hitron route and wait for the Polaris BSSID plus wlp8s0 route").
